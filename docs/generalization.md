# 泛化：怎么让"验证"这件事不绑定领域

> **一句话**：引擎**不认识你的领域**。它只认识「结论类型」——
> 极值、全称断言、最优性、极限……而"这类结论该怎么验"是与领域无关的知识。
> 把这份知识结构化，泛化就成立了。

## 一、为什么之前不泛化（问题在哪）

早期版本的 `mm` 其实只是个"记账壳子"：

| 症状 | 后果 |
|---|---|
| 求解器是**每个案例手写**的 `solve.py` | 加一个难题就要写一遍解题代码（本来如此，不冤） |
| 七条协议只写在 `prompts/*.md` 里，是**给人看的文字** | 机器不知道你到底跑没跑，"验证"靠自觉 |
| 台账里 `protocols: ["P1","P3"]` 是**人填的数组** | 填错了也没人拦，可以自称已验证 |

于是每换一个领域，验证逻辑就要从头再来一遍——**规模上不可能泛化**。

## 二、现在的三条支柱

### 支柱 1：结论类型 → 必跑检查（`mm/checks.py: REQUIRED_BY_KIND`）

这是**可积累、可评审的领域无关知识**：

| 结论类型 | 必跑 | 典型失效模式 → 对应手段 |
|---|---|---|
| 等式 | P1 | 单条推导写错 → 双路径交叉 |
| 恒等式 | P1 + P4 | 边界情形不成立 → 极限检验 |
| 极值 | P1 + P3 | 极值在窄峰上，网格取不到 → 连续复核 |
| 最优性 | P1 + P3 + P5 | 局部最优冒充全局最优 → 反例搜索 |
| **全称断言** | **P2 + P5** | 粗采样整段跳过窄违例带 → 对抗搜索 + 翻转边界 |
| 覆盖 | P2 + P3 + P5 | 同上，且最坏点在边界上 |
| 存在性 | P5 | 只在特定区域存在 → 边界搜索 |
| 唯一性 | P4 + P5 | 退化情形下多重解 |
| 极限 | P4 | 收敛但不退化到已知结果 |
| 单调性 | P1 + P5 | 区间内反向 |
| 稳健性 | P5 | 扰动下翻转 |
| 统计量 | P6 | 口径混用 |
| 预测 | P5 + P6 | 样本外失效 + 口径外推 |
| 口径相关 | P6 | 不同口径直接相减 |

**强制力**：一条结论标了 `verified`，如果它这一类该跑的协议没跑齐，`mm solve` **直接报错**。
—— 不许一条"全称断言"只跑 P1 就自称已验证。

### 支柱 2：可执行检查器（不是提示词，是函数）

七个检查器都对**结论类型**编程，没有一个字提到领域：

| 检查器 | 在做什么（领域无关的部分） |
|---|---|
| P1 | 两个任意对象（标量/序列/字典递归）的相对误差是否 < 判据 |
| P2 | 用"固定网格"和"对抗搜索"两路找同一函数的最坏点，**不一致就报窄带陷阱** |
| P3 | 离散极值 vs 连续搜索复核，并报出平台区间 |
| P4 | 一串"参数→实测 vs 期望退化值"的极限检验 |
| P5 | 对任意判据函数二分求**翻转边界**；找不到就如实报未覆盖 |
| P6 | 一组并列数字是否各自带口径、是否跨口径可比较 |
| P7 | 台账对账（已有） |

### 支柱 3：声明式绑定（案例只写"钩子"）

```jsonc
// ledger.spec.json
{
  "id": "B-001",
  "kind": "全称断言",                       // ← 决定必跑哪些协议
  "claim": "…最坏点 x = {{m.coverage_now.worst_point_x|.2f}} m…",   // ← 数字来自 metrics.json
  "checks": [
    {"protocol": "P2", "fn": "cover_margin_aged", "lo": 0, "hi": 2000, "base_n": 51}
  ]                                              // ↑ verify.py 里的钩子名
}
```

案例侧只提供钩子，引擎侧完全不用改：

```python
# verify.py —— 领域知识全在这里
def cover_margin_aged(x):
    return solve.nearest_gap(x, solve.stations(solve.N_NOW)) - solve.R_AGED
```

## 三、加一个全新领域的难题：三步

```bash
mm charter new  mycase/charter.md      # 1. 填 12 节问题说明书（卡点①，机器校验）
                                        # 2. 写 solve.py（数字只出口到 out/metrics.json）
                                        #    写 verify.py（把可检查的对象暴露成钩子）
                                        #    写 ledger.spec.json（每条结论声明 kind + checks）
mm solve mycase                        # 3. 引擎自动跑检查、填台账、渲染报告
mm audit mycase                        #    临时目录独立重跑 + 逐数字/逐检查对账
```

一个最小案例只要 6 个文件：`charter.md` / `solve.py` / `verify.py` /
`ledger.spec.json` / `report.template.md` / `expected.json`。

## 四、它到底泛化到什么程度（诚实边界）

**能泛化**（已被两个案例验证）：

| | 案例 A `newsvendor_inventory` | 案例 B `sensor_coverage` |
|---|---|---|
| 数学族 | 随机优化（期望值、离散决策） | 几何 / 全称断言（连续、∀ 量词） |
| 结论类型组合 | 统计量 / 等式 / 极值 / 稳健性 / 口径相关 | 全称断言 / 极值 / 覆盖 / 稳健性 / 极限 |
| P2 是否触发 | 未触发（无全称断言） | **触发，且自动识别出窄带陷阱** |
| 台账 | 9 条（8 证 + 1 证伪留痕） | 7 条（6 证 + 1 证伪留痕） |
| 引擎改动 | — | **零** |

**不能泛化（必须留给人/模型）**：

1. **怎么建模**。"这个难题该用什么数学"穷举不了——那是方法论、经验与创造力的活。
   工具只做它的对偶问题："怎么知道它是对的"。
2. **钩子要有人写**。把"可检查的对象"暴露出来，仍然需要理解问题的人动一次手。
   这一步无法自动化，只能做到**又小又规范**（一个案例通常 5~10 个钩子）。
3. **搜索无法保证找到任意窄的特征**。有限预算的对抗搜索也只是一个"更好的网格"：
   无坡度的孤立尖峰会漏。所以 P2 每次都把**搜索分辨率**一起报出来，并把"未找到"
   读作"在该分辨率下未找到"，绝不写成"已证明成立"。
4. **结论类型表是经验知识，需要持续积累**。它的条目来自一次次真实翻车；
   新类型要靠社区贡献，而不是靠"自动学习"。

## 五、什么时候该加什么

| 遇到的情况 | 该加什么 | 为什么 |
|---|---|---|
| 有一类结论反复出现，但表里没有它的类型 | **加一条 `REQUIRED_BY_KIND`** | 泛化知识应该沉淀在表里，而不是散在案例里 |
| 有一种"这类结论总是这样坏"的失效模式，现有检查器打不到 | **加一个检查器** | 检查器是"手段"，手段可以复用给所有领域 |
| 只是这个案例特有的验证 | **写在案例的 `verify.py` 里** | 不要污染引擎；领域知识归案例 |
| 只是口径不同 | 不要加类型，**加口径声明** | 口径分歧靠并列报出解决，不靠新机制 |

## 六、一条判据

> 如果一个改动**让引擎里出现某个领域的名字**（库存、管廊、促销、探测半径……），
> 那就改错了地方——领域知识必须留在案例的 `verify.py` 里。
>
> 这个判据在两个案例上都成立：`mm/checks.py` 里没有一处提到具体问题。
