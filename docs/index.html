会自我证伪的
建模助手

它不承诺"算得对"。它承诺：你分得清哪一句是真的—— 每条结论都有状态、有证据、有一条能重算出它的命令。

所有"AI 建模"工具都在解决怎么写出来（调 API 谁都会，这片是红海， 还跟学术诚信打架）。TroubleSolver 解决的是另一个问题： 怎么知道它是对的。 差异化不在生成能力，而在两样东西——验证协议库（主动去找自己的反例） 和可追溯台账（把"可信度"变成可查询的字段）。

7 条验证协议，已是可执行检查器
4 个异构案例，引擎零改动（库存随机 / 设施覆盖 / 信贷风控 / 渔业资源）
53 项测试，含一组"故意做错看会不会放过去"的负例
100%交付数字来自脚本，零手写

思维导图

一张图看懂 TroubleSolver

中间是它要解决的问题，左右六条主干分别是：为什么做、怎么记账、什么不做， 以及协议、流程、交付物。点任意主干可跳到对应章节，鼠标悬停会高亮该分支。

快速开始

怎么用：一条命令跑通一个闭环

核心闭环不需要 API key、不需要数据库、不需要服务端 —— 一个案例 = 一个文件夹， 状态全在文件里，看得见、改得动、能回滚。 只有可选的 LLM 编排（tsolve agent）才需要一个 key，且只从环境变量读，代码里搜不到。

拿到代码，跑起来

不装也能跑（把 src 加进模块路径即可）；想用 tsolve 这个短命令就本地安装。

git clone <repo> && cd trouble-solver # 方式一：免安装 PYTHONPATH=src python -m troublesolver.cli --help # 方式二：装成命令（开发模式） pip install -e . tsolve --help

先写《问题说明书》——这是卡点①

生成模板 → 填 12 个小节 → 机器校验。不通过就不许进入建模： 因为 90% 的返工都源于"问题没问全"，而不是"算错了"。

tsolve charter new mycase/charter.md # 生成 12 节模板 # …… 填：现象/目标/决策/约束/数据/成功标准/时间尺度/相关方/ # 已有尝试/边界/风险与底线/口径表；【未知】项必须给出处理计划 tsolve charter check mycase/charter.md # 卡点①：不通过则退出码 2

备好四件套，然后 tsolve solve

求解脚本只负责算，把数字全部写进 out/metrics.json； 报告模板只负责说，数字一律写成占位符。二者由工具焊在一起。

tsolve solve mycase # 形式化 → 基线 → 建模 → 证伪 → 台账 → 交付 tsolve audit mycase # 临时目录独立重跑 + 逐数字对账 + 状态漂移检查 tsolve ledger check mycase/ledger.json # 只查台账（快）

把结论钉在台账上

每条结论一个条目：状态、方法、跑过哪些协议、口径、证据文件、重算命令、依赖。 报告只能引用 verified 的条目。

tsolve ledger show mycase/ledger.json # 看全部结论与状态分布

产品本体

七条验证协议

不是提示词技巧，而是可执行、带判据、能自动跑的检查。 其中 P2 / P3 / P5 是"主动去找自己的错"，也是真正的门槛—— 它们要求的不是算力，是对抗自己的意愿。

#协议判据来历（实战翻车）
P1双路径交叉 同一结论用两种独立方法实现（解析式 / 数值 / 仿真），相对误差 < 1e-9；不通过就查哪一路写错，两路都进台账 闭式解与半平面交互相印证
P2细步重扫 凡出现"恒成立 / 一定 / 总是 / 从无例外"：步长细化 ≥10× 重扫，并主动构造最坏构型 3° 步长跳过宽 2° 的违例带，得出"恒成立"的假结论；0.1° 细扫后结论被推翻
P3连续复核 离散网格算出的极值必须用连续 / 自适应搜索复核，报区间，禁止报单点 网格峰值 vs 连续上确界只差 0.0001，但固定网格会把"很小的正数"误报成 0
P4极限与量纲 参数 → 0 / ∞ / 临界值时须退化为已知结果；量纲自洽 临界值处判据恰好取等，可用于反查公式
P5反例搜索 主动搜使结论翻转的参数区域，报"翻转边界"；找不到也要写明搜索范围与未覆盖区域 外环相位偏移半步，就能让"零盲区"变成相反结论
P6口径声明 每个数字标：来源 / 定义 / 适用边界 / 能否外推；有分歧的两套都算，禁止相减 虚拟时间与官方测试数字量纲不同，差点进同一张表比较
P7台账对账 对外每个数字都能由一条命令从原始数据重算，禁止手抄 所有统计值由脚本产 JSON，报告读 JSON

「未触发」要写出来

没出现"恒成立"类断言，不等于不用检查——是检查了才发现不需要 P2。 留空 ≠ 通过，留空只是没人知道你做没做。

「未覆盖」要写出来

搜不到反例时，写清搜索范围与没覆盖的区域， 而不是写"未发现反例"。

「已证伪」要留痕

删掉错误结论等于让同一个错误再来一次。 台账里的 refuted 是资产，不是污点。

第二个护城河

可追溯台账：把"可信度"变成字段

AI 建模最大的信任问题不是"算错"，而是分不清哪句是真的。 台账把这件事变成一个可查询、可校验、可传播的字段。

new→ verifying→ verified ✓ 可被引用  │ 上游改动 →  stale 作废待重验  ／  refuted 已证伪（留痕，不删）

一条台账长什么样

{ "id": "C-017", "claim": "环覆盖证书在 (ρ=980, n=8) 下成立，最大未覆盖距离 970.03 m", "status": "verified", "method": "解析不等式 + 网格枚举（0.1° 细扫）", "protocols": ["P1", "P3"], "caliber": { "定义": "d_max = 环上相邻站角平分线处的最坏距离", "适用边界": "R=1800, r_min=1000；ρ>r_min 时不成立", "可外推": false }, "evidence": ["out/metrics.json", "report.md"], "recompute": "python solve.py", "depends_on": ["C-005", "C-007"] }

对账规则（缺一即报错）

  • 证据文件存在——不是"我记得有"
  • 有重算命令——没有重算命令的结论等于口说无凭
  • 有口径定义——同一个数字换个口径可能是另一个意思
  • 依赖干净——不得引用已证伪 / 已作废的条目

stale 沿依赖链传播

改一个上游参数，invalidate() 会把这条 及其全部下游一起置为 stale。机器告诉你哪些结论已经过期， 而不是靠人回忆"这条是不是也受那个参数影响"。

为什么 audit 必须在临时目录重跑：同目录重跑留了一个隐蔽的作弊面—— 上一步的产物还在原地，"重跑"可能只是读了上次的结果。复制到临时目录、 让 out/ 不存在再跑，才是真正的从原始数据重算一遍。

P7 的执行体

数字零手写：不是靠自觉，是靠跑不过去

"报告里的数字必须来自脚本"这句话，如果只写在文档里，等于没写。 TroubleSolver 把它做成构建期硬失败：模板里只能写占位符，取不到值就报错退出， 连留空的机会都没有。

模板里这样写（不允许出现任何手写数字）

建议每周备货 {{m.result.recommend_Q}} 件， 相对基线多 {{m.result.gain_vs_baseline_per_week|.2f}} 元/周 （+{{m.result.gain_vs_baseline_pct|.1f}}%）， 失效边界：促销概率 ≥ {{m.P5_counterexample.flip_point|.0%}}

渲染出来的成品

建议每周备货 133 件， 相对基线多 50.85 元/周 （+5.0%）， 失效边界：促销概率 ≥ 25%

格式交给 Python（.2f / .1% / ,.0f）， 数字交给 metrics.json，人只负责写字。

三个容易漏的后门（都已堵上）

  • 口径字段里的数字：caliber.适用边界 常写"概率 ≥ 某值即失效"， 若只渲染 claim，口径就成了手抄的后门 → 递归渲染整棵树
  • 错别字会静默漏过：占位符路径原本只认 ASCII， {{m.需求}} 这类写错会既不报错也不替换 → 改为匹配任意路径字符
  • 注释里的示例：模板开头的说明注释写了占位符示例，会被当成本尊去找值 → 渲染前先剥离注释，注释也不进交付物

还有个隐蔽的坑

JSON 键名不要带点号。 写成 profit_band_0.1pct，占位符路径 m.P3_continuous.profit_band_0.1pct.0 就会被点号切断，渲染期直接报"取不到值"。改成 profit_band_0p1pct 即可。

这不只是洁癖：它会在跑的时候炸出来，而不是在交付之后被人发现。

泛化

引擎不认识你的领域，只认识"结论类型"

这是它敢说"能解决各种各样的难题"的全部底气：协议不是写在提示词里给人看的文字， 而是能跑的检查器。引擎只认结论类型——等式、极值、全称断言、最优性—— 而"这类结论该怎么验"这件事与领域无关。把它结构化，泛化就成立了。

结论类型必跑它防的是什么
等式P1单条推导写错 → 双路径交叉
极值P1 + P3极值在窄峰上，网格取不到 → 连续复核报区间
全称断言P2 + P5粗采样整段跳过窄违例带 → 对抗搜索 + 翻转边界
覆盖P2 + P3 + P5同上，且最坏点常落在边界上
最优性P1 + P3 + P5局部最优冒充全局最优
稳健性P5扰动下结论翻转而没人知道
统计量P6口径混用（数字可复算由 P7 兜底）
极限P4收敛了，但不退化到已知结果
口径相关P6不同口径的数字被直接相减

加一个全新领域的难题：三步

诚实边界（不能泛化的部分必须说清楚）： ① 怎么建模穷举不了——那是方法论与创造力的活，工具只做它的对偶问题"怎么知道它是对的"； ② 钩子要有人（或 LLM）写、有人过目——tsolve agent 能让 LLM 读 charter.md 生成 solve.py / verify.py / 台账，但它们仍走完全相同的引擎闭环，且"钩子暴露得对不对" 最终仍需理解问题的人过目一道；引擎只保证"结论不可作弊"，不替人担保"建模一定对"； ③ 搜索无法保证找到任意窄的特征——所以 P2 每次都把搜索分辨率一起报出来， 把"未找到"读作"在该分辨率下未找到"，绝不写成"已证明成立"。

防护实测

不是"设计了防护"，是"防护真的会拦"

测试里专门留了一组负例——故意把事情做错，看工具会不会放过去。 下面四个是真实输出（覆盖：参数漂移、卡点①、模板占位符、跨领域反例自动抓取）。

① 悄悄改一个参数（价格 25 → 26）

同一个案例重跑，数字必然会变。审计会逐项报出来，逼你显式确认这次漂移是"有意的"。

② 用户还没确认口径（卡点①）

③ 模板里写了一个不存在的键

不是静默留空，是直接失败——不给"猜一个数字印上去"留任何空间。

园区步道照明覆盖案例里有一条断言：「实测（光衰后）半径下现状布点仍覆盖全长」。 51 点均匀网格（步长 40 m）判它成立；引擎的对抗搜索在 x=833.333 m 处找到了约 7 cm 宽的照度缺口， 并当场把"网格在骗人"这件事写进结论。

$ tsolve solve examples/facility_coverage 【阶段 3 证伪】自动执行检查 12 条：通过 11，不通过 1 ⚠️ [P2] 实测半径下的覆盖断言：不通过 网格(51 点/步长 40) 最坏裕度 -6.600e+00 → 对抗搜索最坏裕度 6.667e-02 @ x=833.333 ⇒ 断言被证伪；⚠️ 网格给出的是假结论（窄带陷阱：真反例落在网格点之间）
再加上一组常规测试覆盖：空白《问题说明书》必须判不通过、【未知】项没有处理计划必须拦、 标 verified 却没证据 / 没重算命令 / 没口径定义必须拦、引用已证伪条目必须拦、 refuted 条目本身不报错（它是留痕不是错误）、依赖链 stale 传播不影响无关条目。

边界

它不做什么（明确砍掉）

产品文案避免"保证最优"，改成"给出可验证的次优解 + 失效边界"。 同样地，功能清单里"不做什么"和"做什么"一样重要。

✓ 做

  • CLI 一条命令跑通单个问题的完整闭环
  • 七条验证协议 + 台账（状态机 / 对账 / stale 传播）
  • 输出报告 + 证伪记录 + 台账 + 一键复现脚本
  • 报告强制包含"局限与失效边界"章节
  • 本地文件为唯一状态，没有隐藏状态

✗ 不做

  • 生成竞赛论文（红海，且与学术诚信冲突）
  • Web UI / 前端 / 账号体系 / 支付
  • 多智能体角色扮演（Persona 花活）
  • 数据库 / 向量库 / 服务端
  • 对接外部业务系统（留给社区）
定位提醒：它不是"自动解题神器"。它不替你想模型，也不替你写数字； 它做两件事——卡住不该往下走的（两个人工卡点）， 以及把结论钉在脚本上（台账 + 占位符）。
