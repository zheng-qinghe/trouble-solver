# 阶段 5：交付

> 交付物不是"一份好看的报告"，而是**一份别人能自己重算出全部数字的解答包**。
> 报告里可以有一句话说不清的地方，但**不能有一个数重算不出来**。

## 一、交付包清单

| 文件 | 角色 | 谁看 |
|---|---|---|
| `report.md` | 结论 + 基线对照 + 验证记录 + **局限与失效边界** | 决策者 |
| `falsify.md` | 证伪记录（七条协议逐条留痕，含未触发/未覆盖的显式声明） | 复核者 |
| `ledger.json` | 可追溯台账（每条结论的状态／证据／重算命令／口径） | 复核者、接手的人 |
| `out/metrics.json` | 全部数字的唯一出口 | 机器 |
| `solve.py` | 一键复现 | 任何人 |

## 二、硬性规则

1. **"局限与失效边界"章节必须有**，且内容只能来自 `falsify.md`，**不得由模型自由发挥**
   （模型一发挥就会写出"总体表现良好"这种没信息量的话）。
2. **报告只能引用 `verified` 的台账条目**。`refuted`（已证伪）和 `stale`（上游改动后作废）
   的条目**必须留在台账里**——它们是"我们试过、错了"的证据，删掉就等于让同一个错误再来一次。
3. **数字零手写**。报告的每个数字都是 `{{m.路径}}` 占位符；占位符取不到值 → 构建失败，
   不是"空着先发出去"。
4. **口径必须与数字同行出现**。凡出现不同来源的数字并列，必须紧跟口径声明；
   **不同口径的数字不得相减**。
5. **不写"最优"、写"在什么口径与假设下的最优解"**；不写"保证"，改说"可验证的次优解 + 失效边界"。
6. **交付质量自检**（从实战踩坑固化）：交付前跑一遍
   `mm ledger check` + `mm audit`；
   若交付物含 PDF/图片，另需检查页数上限、落纸字号、缺字形（tofu）、身份信息脱敏。

## 三、验收命令

```bash
mm solve <case_dir>     # 卡点① 卡点② 台账 占位符注入，全过才算跑通
mm audit <case_dir>     # 临时目录独立重跑 + 逐数字对账 + 状态漂移检查
mm ledger check <case_dir>/ledger.json   # 只查台账（快）
```

三者的区别要讲清楚：
- `mm solve` 回答"**这份交付物是不是从脚本长出来的**"；
- `mm audit` 回答"**换台机器、换个时间重跑，数字还一样吗**"（阶段 6，独立复核）；
- `mm ledger check` 回答"**每条结论有没有证据、有没有重算命令、有没有引用已作废的结论**"。

## 四、反模式（出现即打回）

| 反模式 | 为什么错 |
|---|---|
| 报告里"由于篇幅原因省略验证过程" | 验证过程才是这份交付物的价值本体 |
| 只报成功的那条路径 | 另一条路径的结果是可信度的一部分，藏起来就是欺骗 |
| 把 refuted 的条目从台账删掉 | 下次还会踩同一个坑，而且没人知道踩过 |
| 交付"最优方案"不提失效条件 | 失效条件不知道，方案就不能落地 |
| 让模型"润色"报告数字 | 润色 = 改数 = 台账立刻失效 |
